# 跨系统转移协议实验库

这是一个只使用虚拟余额的 Go 实验项目，在两套本地模拟账本上实现 HTLC 风格的双边锁定、领取与超时退回。

## 存储隔离

- `ledger-a/accounts.json`、`ledger-b/accounts.json`：各自账本的账户余额。
- `ledger-a/escrows.json`、`ledger-b/escrows.json`：各自账本上的锁、领取、退回状态。
- `protocol/instances.json`：协议实例和跨链协调状态。
- `network/messages.json`：消息发送、延迟、投递与断连积压记录。
- `node-a/messages.json`、`node-b/messages.json`：节点已处理消息集合，重复消息只生效一次。

协议实例只是缓存和协调视图；重启后会重新查询两套实际账本中的 escrow 状态并更新协议阶段，不只相信协调者日志。

## 安全规则

- 领取必须提交与 `hash_lock` 匹配的 secret，且不能超过本地账本截止时间。
- 退回必须等到本地账本截止时间之后。
- escrow 进入 `claimed` 后不能退回，进入 `refunded` 后不能领取。
- 相同消息 ID 重复到达时，节点直接忽略，不重复扣款或加款。
- 两侧时钟偏移会换算进各自本地 deadline；消息确认延迟和链路中断由模拟网络控制。

## 多笔并发与资金占用

- 同一参与者可同时发起多笔转移；锁定立即从账户余额扣减并记入 escrow，已锁住的金额不能再用于另一笔，余额不足的一侧返回 `ErrInsufficientFunds` 且不形成锁。
- `Ledger.LockedBalance` / `AvailableBalance` 汇总每个账户当前仍被锁住与可支配的虚拟金额。
- 两侧可能出现非对称的部分锁定：A 侧资金不足没锁上、B 侧金库充足已经锁上，反之亦然，协调者只能按两侧账本实际状态逐笔处理。
- 领取与退款相撞时，账本互斥保护单个 escrow：截止前先到的 `claim` 成立后，迟到的 `refund` 返回 `ErrAlreadyFinal`；超时后的 `refund` 成立后，迟到的 `claim` 同样被拒，只形成一个有效终态。
- 重复消息在两个层面幂等：节点按消息 ID 去重，账本对相同 escrow 的重复锁定/领取/退款也不重复扣款加款。

## 失联恢复与逐笔对账

- 协调者长时间失联后必须以全新进程重新打开两侧账本，`ReconcileReport(transferID)` 强制重读 escrow，不能只依据过期协调日志继续发款。
- 报告逐笔给出：协议阶段、两侧各自的锁定金额、本地时钟、截止点、剩余/超期时长，以及当前允许的动作（窗口内 `claim`、超时后 `refund`、缺失时是否可 `resend_lock`、终态 `none_final`）和动作时间窗。
- `RecoverMissingLocks` 只对账本上确实缺失且本地截止未到的一侧补发锁定；已锁定侧不重复扣款，已过期侧直接跳过并走退款。

## 运行

```bash
go test ./...
go run ./cmd/lab -dir labdata
```

默认演练覆盖五个阶段：领取/退款相撞的单一终态、正常领取、B 断连下同一参与者同时发起三笔转移（其中一笔因资金已被占用锁不上、形成非对称部分锁定，且积压消息重复）、协调者失联 4 小时后重启逐笔重读两侧账本出报告、恢复后投递积压消息并按报告逐笔领取或超时退回。最终打印每笔转移仍被锁住的金额、可采取的动作与时限，以及两侧账户锁定/可用汇总。

项目不接入真实网络、真实账本或真实资产，仅用于验证协议状态机和故障演练。
