# 跨系统转移协议实验库

这是一个只使用虚拟余额的 Go 实验项目，在两套本地模拟账本上实现 HTLC 风格的双边锁定、领取与超时退回。

## 存储隔离

- `ledger-a/accounts.json`、`ledger-b/accounts.json`：各自账本的账户余额。
- `ledger-a/escrows.json`、`ledger-b/escrows.json`：各自账本上的锁、领取、退回状态。
- `protocol/instances.json`：协议实例和跨链协调状态。
- `network/messages.json`：消息发送、延迟、投递与断连积压记录。
- `node-a/messages.json`、`node-b/messages.json`：节点已处理消息集合，重复消息只生效一次。

协议实例只是缓存和协调视图；重启后会重新查询两套实际账本中的 escrow 状态并更新协议阶段，不只相信协调者日志。

## 安全规则

- 领取必须提交与 `hash_lock` 匹配的 secret，且不能超过本地账本截止时间。
- 退回必须等到本地账本截止时间之后。
- escrow 进入 `claimed` 后不能退回，进入 `refunded` 后不能领取。
- 相同消息 ID 重复到达时，节点直接忽略，不重复扣款或加款。
- 两侧时钟偏移会换算进各自本地 deadline；消息确认延迟和链路中断由模拟网络控制。
- 同一参与者的多笔转移可并发进行；锁定时立即从可用余额中扣减，已锁资金不能再次用于另一笔，余额不足的新锁定会被拒绝。
- 领取与退款在截止点相撞时，账本互斥保证只形成一个有效终态，不会双重支付。

## 分次领取

- 接收方可分多次领取：每次携带协调者决定的 claim_id 与本次金额，第一次领取只进入 partially_claimed（一部分已结清），领满才是 claimed（整笔完全结束）。
- 每笔领取留下可追溯记录：本次金额、已确认总额、仍不确定的剩余部分；协调者分别记录两侧事实，状态为 confirmed、rejected 或 pending。
- 相同 claim_id 的重复请求或丢失后重发的回应直接返回首次记录，不重复扣款、加款。
- 决定边界清晰：领取仅在严格早于本地截止时接受，退款仅在到达截止后执行；截止后迟到的领取会形成带原因的 rejected 记录，不会永久卡在未知。
- 退款前必须先追查所有 pending 领取；待定金额不会同时计入可退余额。单侧确认、另一侧迟到拒绝时进入 claim_conflict，争议金额保持锁定，只退回两侧无争议的剩余部分。
- 领取在账本互斥锁内原子记账；已确认部分不撤销、不重复领取，争议解决前不能把整笔错误结清。
- 协调者把每次领取决定（claim_id、金额、消息 ID）持久化；重启后用原编号重发同一决定并从实际账本读回确认状态，不以新编号重做可能已发生的效果。
- Ledger.TotalBalance()+Ledger.LockedTotal() 用于核对每个账本余额与锁定之和守恒。

## 逐笔对账

`Coordinator.Audit()` 重新读取两侧实际账本（而非协调者过期日志），对每笔进行中的转移给出：

- 两侧 escrow 状态与仍被锁住的金额；
- 已确认、待确认、争议锁定、可退金额，以及当前可采取的动作（`claim`/`refund`/终态）及其本地时限；
- 协调者长时间失联重启后，先用它核实再继续发款。

## 运行

```bash
go test ./...
go run ./cmd/lab -dir labdata
```

默认演练中，alice（余额 1000）同时发起四笔转移（100、250、600、100），第四笔因前三笔已占用 950 而被拒绝。随后 B 侧断连，协调者失联 90 分钟后重启，从两套实际账本逐笔对账：demo-1 已过截止可退款，demo-2、demo-3 仍可领取。恢复连接后过期的 B 锁定消息被拒绝，demo-1 在 A 侧退回，最终为 `partially_refunded`。

项目不接入真实网络、真实账本或真实资产，仅用于验证协议状态机和故障演练。
